# Performance Test Plan

**Version:** 1.0 (2026-11-10) · **Parent:** [MASTER-TEST-STRATEGY.md](MASTER-TEST-STRATEGY.md) · **Targets:** NFR-G-01…NFR-G-05, NFR-G-09 ([DOCUMENTATION-CONVENTIONS §7.1](../DOCUMENTATION-CONVENTIONS.md)) and module NFRs in each spec

## 1. Objectives

1. Verify the latency and throughput targets under the target load profile.
2. Verify that correctness invariants (no oversell, ledger = balance) hold **under load**, not only in functional tests.
3. Establish baselines per release and detect regressions above 10% in p95.
4. Size the production deployment (DEPLOYMENT-ARCHITECTURE scaling path).

## 3. Load profile (target: MVP = 1 org/2 branches; V1 = 50 branches)

| Workload | Share of requests | Rate at V1 peak |
|---|---|---|
| POS search + barcode lookup | 55% | 1,000 cashier sessions × 1 search / 4 s ≈ 250 rps |
| Sale quote | 15% | ≈ 70 rps |
| Sale completion | 8% | 1,000 cashiers × 1 sale / 60 s ≈ 17 sales/s |
| Stock queries, prescriptions, patients | 15% | ≈ 70 rps |
| Back-office (receiving, transfers, reports) | 7% | ≈ 30 rps, plus 2 concurrent report exports |

MVP gate uses the same scripts at 2 branches × 5 cashiers. V1 gate uses the full table.

## 4. Test data volume

Generated by the volume seeder (TEST-DATA-STRATEGY §5): 2 organizations; the large one has 50 branches, 50,000 medicines, 500,000 batches, 20 M stock movements, 500,000 sales/year, 500,000 patients, 1 M prescriptions, and 50 M audit rows. Arabic and English names follow realistic distributions, including common prefixes, to stress trigram search.

## 5. Test types

| Type | Description | Duration | Frequency |
|---|---|---|---|
| Baseline | Target profile at 100% | 30 min | Weekly (performance env) |

| Job concurrency | Nightly jobs while 50% POS load runs | 60 min | Pre-release |
| Frontend | Lighthouse CI on login, POS, receiving; bundle-size budget | Per PR (budget), weekly (Lighthouse) | — |

## 6. Contention test (CS-01 under load)

- **Hot items:** 10 fast-moving medicines, each with 3 batches, plus a scenario with only 1 unit left.
- **Load:** 200 virtual cashiers across 10 branches; 30% of carts contain a hot item, and multi-line carts list items in random order.

**Assertions:**
- Oversell is zero: after the run, Σ sold per batch ≤ received for that batch, and INV-01/02 pass on the whole database.
- Unhandled deadlocks are zero. Deadlock retries stay below 0.1% of sales, and lock timeouts (503 `COMMON.LOCK_TIMEOUT`) stay below 0.5%.
- Sale completion p95 stays within PT-04 for non-hot carts, and p95 ≤ 1.5 s for hot carts.
- Branch invoice-number serialization: the last step of a sale holds the per-branch counter lock for ≤ 20 ms p95. This is measured with `pg_stat_activity` sampling and addresses the EPIC-06 risk on counter serialization.

## 7. Tooling and environment

| Item | Choice |
|---|---|
| Load generator | k6 (JavaScript scenarios in `tests/performance/`), executed from a separate VM |
| Metrics | OpenTelemetry → Prometheus/Grafana dashboards (API latency, DB, locks, GC, thread pool); `pg_stat_statements`, `auto_explain` (threshold 200 ms) |
| Environment | Same container images as production; DB sizing per DEPLOYMENT-ARCHITECTURE; isolated from other tests |
| Auth | Pre-issued tokens per virtual user; refresh exercised at 10% of sessions |
| Idempotency | Every completion carries a unique Idempotency-Key; 1% of requests are deliberate duplicates (assert single effect) |

## 8. Reporting and gates

- Each run publishes p50/p95/p99, error rate, throughput, DB CPU/IO, lock waits, top 20 queries, and a comparison with the previous baseline.
- **Release gate (G9):** PT-01…PT-05, PT-08, and PT-09 are met at the release's target profile, the contention test passes, and no regression above 10% p95 against the previous release without an accepted justification.
- Any failed target opens a performance defect. A failure of PT-04 or the contention test blocks release.
